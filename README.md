# Hostingwebsite — Render Deployment

## Deploy on Render

1. Push this project to a GitHub repository.
2. Open the Render Dashboard and choose **New + → Blueprint**.
3. Select the repository containing this project and deploy the `render.yaml` blueprint.
4. In the Render service's **Environment** settings, fill in the values below, then redeploy.

## Required environment variables

- `FIREBASE_KEY_JSON`: Full Firebase service-account JSON, pasted as one JSON value. Keep it secret; never commit it to GitHub.
- `FIREBASE_STORAGE_BUCKET`: Firebase Storage bucket name from your Firebase project.
- `ADMIN_EMAILS`: Admin email addresses separated by commas. Use the exact email you sign in with.
- `FB_API_KEY`, `FB_AUTH_DOMAIN`, `FB_PROJECT_ID`, `FB_STORAGE_BUCKET`, `FB_SENDER_ID`, `FB_APP_ID`: Firebase **Web app** configuration values used by the browser login page.
- `SECRET_KEY`: Generated by the Render blueprint. Do not publish it or change it casually.

Firebase setup must have **Authentication** enabled for the sign-in provider used by the site's login page, **Cloud Firestore** created, and **Firebase Storage** configured if you want script/QR file storage. Check your Firebase security rules and service-account permissions before production use.

## Start/build configuration

- Build: `pip install --upgrade pip && pip install -r requirements.txt`
- Start: `gunicorn -w 1 --threads 4 --timeout 120 -b 0.0.0.0:$PORT app:app`
- Health check: `/health`

The project initializes Firebase when the Flask app starts. If `FIREBASE_KEY_JSON` or required Firebase settings are missing/invalid, startup will fail until you configure them.

## Important Render limitations

- The Blueprint uses Render's **Starter** web-service plan to avoid the free-plan idle-sleep behavior. This is a paid plan; check current pricing in the Render dashboard before deploying. The local filesystem is still ephemeral, so do not rely on local files or child processes surviving a restart/redeploy.
- Firebase Storage is already used by this project for script files, but running uploaded bots are ordinary child processes on the web-service instance. They will stop when the service restarts, and web-service restarts/redeploys will stop them. For reliable bot hosting, use a separate always-on worker service with persistent storage/state as needed.
- The app currently accepts and executes uploaded Python/JavaScript code. Only expose it to trusted users. Running untrusted code on the same host as the website can compromise the service and its secrets; production deployment should isolate each script in a separate container/sandbox with resource limits and restricted network/filesystem access.
- The application needs Node.js for uploaded `.js` scripts. The Python runtime configuration alone does not guarantee Node.js is installed; use a custom Docker image with Node.js if JavaScript bot execution is required.
- Manual UPI/QR payments are not automatically verified by this deployment setup. Verify payments independently before granting a paid plan.

## Local run

```bash
pip install -r requirements.txt
# Set the environment variables listed above first.
python app.py
```


## About cron jobs and the 15-minute sleep

A Render Cron Job runs a scheduled command; it does **not** keep a separate web service awake. The `/health` endpoint is included for monitoring, but repeatedly pinging a free service is not a reliable uptime solution. This Blueprint is set to the paid `starter` plan so the website does not use the free idle-sleep behavior. Review Render's current plan pricing before deployment. Cron is only needed if you have a real scheduled task to run.


## Render Free plan: optional scheduled keep-alive ping

This repository includes `.github/workflows/keep-alive.yml`, which requests the lightweight `/health` endpoint on a best-effort schedule every 10 minutes. To enable it after pushing this project to GitHub:

1. Open your GitHub repository and go to **Settings → Secrets and variables → Actions → Variables**.
2. Click **New repository variable**. Set the name to `TARGET_URL` and the value to your Render service's base URL, for example `https://your-app.onrender.com` (do not add `/health`).
3. Open **Actions** and enable workflows if GitHub asks. Select **Keep Render Web Service Warm** and use **Run workflow** once to test it.
4. Check the workflow run logs; a successful ping should return a response from `/health`.

**Important:** Render Free services are designed to spin down after 15 minutes without inbound traffic. GitHub scheduled runs are best-effort and can be delayed or disabled, so this workaround does **not** guarantee 24/7 uptime and does not keep bot subprocesses reliably running. For guaranteed always-on operation, use a paid always-on service. Do not rely on this for critical workloads.
